# 021. Agent teams: доска, владение, зависимости

- **Статус:** Accepted
- **Дата:** 2026-11-12

## Контекст

Нужны параллельные исполнители с общим планом, но без распределённой системы и внешней БД. Главные риски — двойное выполнение задачи, гонки за владение и зависшие зависимости.

## Решение

1. **Доска в памяти** (`dshr-team`): задачи из YAML, статусы `pending`/`in_progress`/`done`/`failed`, владелец и результат.
2. **Атомарный claim** под `tokio::Mutex`: задача захватывается только если все `depends_on` в `done`; два воркера не получат одну задачу.
3. **Конкурентные воркеры** (1–8), каждый — цикл «claim → субагент → complete/fail». Воркер получает prompt задачи, выводы зависимостей и вход команды.
4. **Ошибка** переводит задачу в `failed`; зависимые остаются `pending` и в отчёте видны как незавершённые. Отмена прекращает цикл.
5. **Изоляция:** `team` регистрируется только у родителя; дочерние агенты не могут запускать вложенные команды.

## Последствия

- Нет двойного выполнения и потерянных зависимостей в рамках одного запуска.
- Доска не переживает рестарт и не принимает новые задачи во время выполнения — это следующий срез.
- Нет бюджетов на воркера и автоматического merge; отчёт — текст + статусы.

## Альтернативы

- Долговечная доска в SQLite — отложено: слабая потребность без демона.
- Динамическое добавление задач — отложено: усложняет завершение и владение.
- Один общий агент вместо воркеров — отклонено: не даёт параллелизма.
