# 043. Reasoning effort на проводе: конфиг соединения, а не запрос

- **Статус:** Accepted
- **Дата:** 2026-11-22
- **Уточняет:** [PARITY](../PARITY.md) §«Web UI: настройки», [MODELS-PORT](../MODELS-PORT.md) этап 3
- **Влияет на:** CONFIG.md, SERVER.md, PARITY.md, MODELS-PORT.md, TECH-DEBT.md, ROUNDS.md

## Контекст

Порт секции Models (`ui-settings-models`, раунды 140–147) довёл до UI и до
`models.yaml` всё, кроме последнего звена: редактор reasoning-уровней сохранял
карту «уровень → значение провайдера», но **ни один адаптер не отправлял
effort в запросе**. Это была записанная строка техдолга, а не осознанная
граница.

Вопрос: где живёт выбранный уровень и как он попадает в тело запроса.

Ограничения:

- `dshr_llm::Request` (`crates/llm/src/types.rs`) — общий wire-тип для обоих
  адаптеров и агента; добавление в него поля тянет `crates/agent` (включая
  литерал `Request` со всеми полями в `title.rs`) и меняет публичный контракт
  ради значения, которое не меняется внутри сессии.
- Уровень — свойство соединения и модели, а не отдельного turn'а: пользователь
  выбирает его в Models, а не в диалоге.
- `run`/`tui`/`acp` собирают адаптеры из env-ключей и сознательно не читают
  `models.yaml`; их поведение менять не договаривались.
- Upstream `0.2.2-rc.3` @ `39163dd` держит effort на `connection.defaults`
  (`reasoningEffort`) и переписывает конфиг на эффективное значение, если
  запрошенное не совпало с фактическим.

## Решение

Effort — **поле конфига соединения**: `DeepSeekConfig.reasoning_effort` и
`OpenAiConfig.reasoning_effort`, обычный `Option<String>` с **значением
провайдера** (тем, что лежит в `models.yaml` справа от уровня), а не локальным
именем уровня. `dshr serve` резолвит цепочку

```
config.yaml → model.reasoning_effort   (локальный уровень)
  → models.yaml → providers.<route>.models[].reasoning_efforts.<level>   (значение провайдера)
  → <Adapter>Config.reasoning_effort     (провод)
```

на старте, рядом с endpoint'ом, ключом и retry-планом. `dshr_llm::Request`,
`dshr_agent` и `title.rs` не тронуты; `run`/`tui`/`acp` продолжают собирать
адаптеры без effort (поле остаётся `None`).

Поведение на проводе (по протоколам):

- **DeepSeek Messages:** `thinking: {type: enabled|disabled}` плюс
  `output_config: {effort}`; для `off` — только `thinking: disabled`,
  `output_config` не отправляется.
- **OpenAI-compatible:** по семейству модели — плоский `reasoning_effort` для
  id, содержащего `gpt-oss`; вложенный `reasoning: {effort}` для прочих
  `gpt-*`; ничего для остальных моделей.
- Отсутствие значения (`None`) означает «параметра нет вообще».

Валидация — до сетевого ввода-вывода: `new()` и `request_body` отвергают
уровень, которого протокол не знает (`LlmError::Config`), без clamp'а и без
подстановки ближайшего. `serve` при этом необъявленный в профиле уровень
пропускает с предупреждением (permissive), а объявленный, но несовместимый с
протоколом — превращает в `DshrError::config`.

В UI — селектор уровня у активной модели с пунктом **Provider default**
(пустая строка → `None` → ключ `model.reasoning_effort` убирается). Селектор
появляется только когда модель объявила ≥ 2 уровня; у модели без
reasoning-метаданных контрола нет.

## Последствия

- Проще: effort меняется без правки wire-типов, агент и все семь
  construction-сайтов `AgentConfig` не задеты; `run`/`tui`/`acp` сохраняют
  прежнее поведение.
- Проще: уровень виден в `GET /v1/config/providers` (блок `active`) и
  перечитывается после сохранения, поэтому селектор не «сбрасывается».
- Платим: `dshr serve` — единственная команда, читающая `model.reasoning_effort`;
  `run`/`tui`/`acp` по-прежнему env-only (записано в TECH-DEBT и PARITY).
- Платим: две осознанные дивергенции от upstream — (а) нет таблиц ремапа и
  per-model `thinkingLevelMap`, значение уходит из `models.yaml` как есть;
  (б) при отсутствии effort адаптер не шлёт reasoning-параметр, тогда как
  upstream подставляет `high` и всегда шлёт `thinking`. Причина (б):
  DeepSeek-адаптер не воспроизводит подписанные thinking-блоки, поэтому
  неожиданный thinking-turn ломает tool-loop.
- Платим: параметр нельзя подтвердить кассетным воспроизведением — первичное
  доказательство это юнит-тесты тел запросов (`llm-deepseek` 15, `llm-openai`
  13) плюс `provider_settings` 10 и живой прогон 14/14 по HTTP-конфигу и UI.
- Проверить при следующем релизе: если upstream начнёт присылать
  `thinkingLevelMap` в каталоге моделей, ремап придётся перенести, иначе
  уровни вроде `xhigh` уедут провайдеру как есть.

## Альтернативы

- **Поле в `dshr_llm::Request`** — отклонён: значение не per-turn, а
  контракт `Request` пришлось бы менять вместе с `crates/agent` и литералом в
  `title.rs`; выигрыша нет.
- **Читать `model.reasoning_effort` внутри адаптеров** — отклонён: адаптеры не
  знают ни `config.yaml`, ни `models.yaml` (они получают готовый конфиг
  соединения), и это протащило бы файловый ввод-вывод в слой протокола.
- **Протянуть effort в `run`/`tui`/`acp`** — отклонён на этом шаге: эти команды
  вообще не читают `models.yaml` (ни endpoint, ни retry), поэтому один
  effort-параметр сделал бы их поведение несогласованным; вопрос вынесен в
  техдолг отдельной строкой.
- **Повторить upstream-дефолт `high`** — отклонён: см. (б) в «Последствиях»,
  плюс молчаливая подстановка противоречит правилу «неподдерживаемый уровень
  падает до сети».
