# 025. Guardrails: бюджет дерева, allowlist, lock

- **Статус:** Accepted
- **Дата:** 2026-11-13

## Контекст

После появления субагентов, workflows и teams один turn может породить много дочерних агентов. Лимиты `max_steps`/`max_tokens` действуют на один агент, но не на дерево; конфиг не позволял ограничить набор инструментов; два scheduler-демона могли выполнять одно расписание одновременно.

## Решение

1. **Общий бюджет токенов** (`Budget`): `Arc<Budget>` в `AgentConfig`, разделяемый родителем и потомками. Перед запросом проверяется остаток, после ответа списываются `input+output`; исчерпание — `AgentError::BudgetExceeded`. Флаг `dshr run --max-total-tokens`.
2. **Allowlist/denylist инструментов:** `tools.allowed` (если непуст — только эти) и `tools.denied` (удаляются всегда). Фильтрация применяется после регистрации всех инструментов, включая MCP/LSP/субагентов; дочерние агенты получают уже отфильтрованный набор.
3. **Scheduler lock:** `ScheduleLock` создаёт `schedules.lock` через `create_new`; второй `schedule daemon` получает ошибку. Lock снимается при выходе.
4. **Авто-заголовок:** headless `run` ставит заголовок из первой строки prompt (до 60 символов), если сессия новая.

## Последствия

- Стоимость дерева можно ограничить заранее; превышение останавливает turn, а не только один шаг.
- Ограничение инструментов работает и для делегированных агентов, а не только для родителя.
- Lock не переживает `kill -9`; stale-файл удаляется вручную (в TECH-DEBT отмечено).
- Авто-заголовок — UX-улучшение, не влияет на журнал.

## Альтернативы

- Бюджет на каждого ребёнка отдельно — отклонено: не ограничивает дерево.
- Фильтрация только в prompt — отклонено: инструмент всё равно доступен модели.
- PID-lock с проверкой процесса — отложено: платформенные различия.
