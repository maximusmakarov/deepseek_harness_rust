# 023. LSP: минимальный клиент и инструменты

- **Статус:** Accepted
- **Дата:** 2026-11-13

## Контекст

Агенту нужна навигация по коду: hover, определения, ссылки и диагностика. Полный LSP-клиент (completion, rename, code actions, workspace folders) — большой слой; для M7 достаточно read-only навигации.

## Решение

1. **Stdio-клиент** (`dshr-lsp`): JSON-RPC с `Content-Length`-фреймингом, фоновый reader, корреляция ответов по `id`, сбор `textDocument/publishDiagnostics`.
2. **Ленивый запуск:** менеджер выбирает сервер по расширению файла и стартует его при первом обращении; серверы кэшируются по имени.
3. **Инструменты:** `lsp_hover`, `lsp_definition`, `lsp_references`, `lsp_diagnostics`. Позиции в инструментах 1-based, в LSP переводятся в 0-based.
4. **Диагностика** приходит асинхронно: `lsp_diagnostics` открывает файл и ждёт 300 мс; это компромисс без отдельного event-loop в агенте.
5. **Границы:** capabilities пустые, нет completion/rename/code actions, нет `didChange` (файл переоткрывается), один сервер на расширение.

## Последствия

- Навигация и диагностика доступны без изменения агентного цикла.
- Ошибки сервера не валят harness: инструмент возвращает текст ошибки.
- LSP-серверы недоверенные процессы; запускаются с cwd workspace, без сети (ответственность сервера).

## Альтернативы

- Полный LSP-клиент сразу — отложено: completion/rename требуют richer capabilities и UI.
- Собственный парсер языков — отклонено: LSP даёт больше за меньшую цену.
- Диагностика через pull (`textDocument/diagnostic`) — отложено: push-модель достаточно.
